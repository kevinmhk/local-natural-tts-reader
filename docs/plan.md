# Build the local document-to-speech reader

This ExecPlan is a living document. The sections `Progress`, `Surprises & Discoveries`, `Decision Log`, and `Outcomes & Retrospective` must be kept current as implementation proceeds. This repository does not yet contain a checked-in `.agents/PLANS.md`; this plan follows the global ExecPlan requirements supplied when it was authored.

## Purpose / Big Picture

After this plan is complete, a user on an Apple-silicon Mac can give the `reader` command a local TXT, Markdown, PDF, or HTML file, inspect the exact cleaned text, and listen to natural Qwen3-TTS speech generated by MLX-Audio entirely on the Mac. Playback starts after the first document chunk is rendered, later chunks generate ahead, and stopping and resuming does not regenerate valid cached audio.

The finished system includes a tested command-line interface and a local drag-and-drop browser interface. It stores all sources, intermediate text, audio, and playback state locally; makes no runtime network request after explicit model setup; and reports documents it cannot safely extract, such as scanned PDFs, instead of silently reading incomplete text.

## Scope

The implementation includes a Python modular monolith, project-local `uv` environment, quality tooling, local artifact workspace, SQLite metadata, format-specific extractors for TXT/Markdown/local HTML/born-digital PDF, conservative cleaning, deterministic chunking, a fake TTS test engine, an MLX-Audio Qwen3-TTS CustomVoice adapter, macOS playback, resumable jobs, a loopback-only API, a React/TypeScript UI, and offline/hardware acceptance tests.

OCR, EPUB, DOCX, remote URL fetching, cloud synchronization, summarization, translation, podcast conversion, native application packaging, voice cloning, and voice design are outside the initial delivery. M4B export and local speech-to-text fidelity checking are stretch milestones and must not delay the core reader.

## Surprises & Discoveries

- Observation: Qwen3-TTS uses distinct model families for preset CustomVoice generation, Base-model voice cloning, and VoiceDesign; these are capabilities, not interchangeable voice options.
  Evidence: The official Qwen3-TTS model table and the MLX-Audio adapter expose separate generation methods for each mode.
- Observation: The current MLX-Audio Qwen adapter documents streaming and batch generation, but upstream interfaces and available converted model IDs can change independently of this application.
  Evidence: The adapter documentation shows BF16 and 6-bit examples while the project-level quick start also uses a Base 8-bit model. Milestone 0 therefore pins a tested pair instead of assuming a model name.
- Observation: PDF text extraction cannot reliably infer semantic structure or OCR image-only pages.
  Evidence: pypdf documents that PDF lacks a semantic layer and that it does not extract text from images. The design requires a preview and an explicit `needs_ocr` outcome.
- Observation: MLX-Audio 0.4.x requires Hugging Face Hub 1.x, which is newer than the planning draft's initial dependency assumption.
  Evidence: `uv sync --group dev` rejected `huggingface-hub<1` because MLX-Audio 0.4 depends on `huggingface-hub>=1.0`; the project bound is now `>=1.0,<2`.
- Observation: MLX-Audio 0.4.8 exposes Qwen CustomVoice through `generate_custom_voice` and successfully loads the selected 6-bit conversion, while Transformers emits a non-fatal model-type compatibility warning during load.
  Evidence: The hardware contract generated a valid WAV and passed; the same warning appeared during both successful real-model runs.
- Observation: The default 6-bit profile stays ahead of real-time playback for the short target-Mac sample.
  Evidence: 147 characters produced 9.23 seconds of audio in 4.14 seconds including process startup and model load, for a real-time factor of 0.45.
- Observation: Short chunks can still trigger Qwen3-TTS's generation cap on unusual extracted passages.
  Evidence: A 262-character PDF chunk reached the cap before emitting a valid completion.

The CLI MVP is operational on the target Apple-silicon Mac. It imports all four MVP formats, preserves inspectable source/extracted/cleaned/chunk artifacts, rejects unsafe PDF and file cases, generates and caches local Qwen3-TTS speech, plays through `afplay`, and resumes only from an unconfirmed chunk. ## Context and Orientation

The repository began with the three planning documents. MVP implementation now adds `pyproject.toml`, a Python 3.12 `.venv`, `src/local_tts_reader/`, `tests/`, scripts, fixtures, and user documentation milestone by milestone. Treat the checked-in working tree and the `Progress` section as authoritative about which paths exist.

The target is a local document reader. An extractor converts one file format into a common structured document. A cleaner removes presentation noise without rewriting meaning. A chunker splits that document into model-sized, ordered passages. A text-to-speech (TTS) engine turns each passage into audio. A playback adapter plays the ordered audio. An artifact store keeps source, text, and audio files, while SQLite records their identities and states so work can resume.

"Content-addressed" means that an artifact path is derived from a cryptographic hash of everything that affects its contents. For audio, that includes chunk text, exact model, voice, language, instructions, speed, generation parameters, and adapter version. A cache hit is safe only when this complete identity matches.

The implementation paths are rooted at `src/local_tts_reader/`. The command-line entry point is `src/local_tts_reader/cli.py`. Domain data and state rules live under `domain/`; orchestration lives under `application/`; external libraries and operating-system behavior live behind adapters in `ingestion/`, `tts/`, `playback/`, and `storage/`. Tests mirror those boundaries under `tests/`. The later frontend lives under `web/` and calls a loopback-only FastAPI adapter; it does not duplicate pipeline logic.

Read `docs/design-and-architecture.md` before each milestone for diagrams and tradeoffs, but keep this plan self-contained whenever a decision is necessary to execute the work.

## Validation and Acceptance

The system is accepted only when all of the following behaviors are observed, not merely when files or classes exist.

1. A TXT, structured Markdown, article HTML, and born-digital PDF fixture each import into immutable source storage and produce reviewed cleaned text with source provenance.
2. A repeated PDF header/footer is conservatively removed and counted; an image-only PDF fails with `needs_ocr`; malformed, encrypted, oversized, and unsupported inputs fail with actionable messages.
3. Chunking is deterministic and reconstructs the spoken cleaned text without omission or repetition. Every chunk respects the configured hard limit unless it carries an explicit forced-boundary warning.
4. The fake end-to-end pipeline passes without MLX, network, or audible output, enabling routine tests on any development machine.
5. On the target Mac, the pinned MLX-Audio and Qwen3-TTS profile generates a valid local WAV whose audio duration and generation metrics are recorded.
6. Playback begins after the first chunk rather than after the entire document; synthesis remains bounded ahead of playback; buffering waits rather than skipping.
7. Pause, process interruption, and resume repeat at most the last unconfirmed chunk and never skip a confirmed chunk. Valid completed audio is not regenerated.
8. Changing only playback session state keeps audio cache hits. Changing the voice or synthesis instruction invalidates audio only. Changing cleaned text invalidates chunks and downstream audio while retaining the source.
9. The local web interface is keyboard-operable, previews exact spoken text and warnings, and completes the same workflow through the application service.
10. With dependencies and weights already installed, the supported workflow succeeds offline and the browser/API bind only to loopback.
11. Logs omit full source text by default, cache pruning is dry-run-first, and failure recovery never exposes partial audio as complete.
12. Ruff formatting, Ruff lint, ty type checking, Pytest, ESLint, TypeScript checking, frontend tests, and Playwright tests all pass in the prescribed order.
13. README and supporting docs match the final commands, data locations, limitations, default model profile, and offline behavior.

No fixed test count is specified before implementation. Each milestone must record the observed pass count and names of new acceptance tests in `Artifacts and Notes`; a reduced count in a later run must be explained.

## Idempotence and Recovery

Environment creation and dependency installation are safe to repeat. All dependencies remain in `.venv` or `web/node_modules`; do not install system or global packages without approval. Model acquisition is explicit, resumable through its upstream cache, and separate from normal `reader` commands.

Import is idempotent by source hash plus import policy.
